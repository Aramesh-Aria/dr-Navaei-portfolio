# SQLite with a persistent disk, not Postgres

Runflare's own deployment guide (https://runflare.com/docs/django-sqlite/) is written around SQLite: point `DATABASES['default']['NAME']` at a file inside a folder, then mount a persistent disk over that folder so the file survives redeploys — it does not document a managed Postgres path. We decided to follow that native path (SQLite + a persistent disk mounted at, e.g., `/app/database`) rather than introduce Postgres ourselves. This site has one write-heavy actor at a time (a content editor in Django admin, or an occasional patient Inquiry) — nowhere near the concurrent-write load SQLite struggles with — so the usual "never SQLite in production" advice doesn't bite here, and matching the platform's documented path means fewer moving parts to debug on a host we're already treating as less familiar (ADR-0002).

Uploaded media (photos) follows the same pattern per https://runflare.com/docs/load-django-css-images/: `STATIC_ROOT`/`MEDIA_ROOT` both live under `BASE_DIR/public/...`, served at `/public/static/` and `/public/media/`, with a disk mounted at `/app/public/media` for uploads only.

**Update (2026-11-14):** static files are no longer on a disk. They are collected locally from `static_dev/` into `public/static/`, committed, and served by WhiteNoise, so `collectstatic` never runs on Runflare (same setup as ArameshMusicAcademy-website). A disk at `/app/public` would hide the committed static files, which is why the media disk is mounted one level down.

**Consequences**: if the site ever needed multiple concurrent writers or heavier traffic, migrating off SQLite to Postgres later is a known but real migration (schema dump/reload, settings change, verifying no SQLite-specific query behavior was relied on) — not a same-day flip.
